# Ship Map Pack v1: `routing`

Roadmap tasks P2.1–P2.5. An optional pack-level block, added without a `specVersion` bump.
Consumers that don't know it ignore it.

`routing` is a small walk/elevator/stairs graph. It is enough for walking directions, walk times
and "leave by" times, offline. It is generated by
[`scripts/routing-graph.mjs`](../../scripts/routing-graph.mjs) from the pack's own decks and
features. Like `entrances`, it is **synthetic**: derived from this repo's synthetic layout, not
traced from an official plan.

## Schema

The block is compact on purpose (see [Size](#size)). Nodes and walk edges are tuples, grouped
per deck, and edges refer to nodes by their index within that deck.

Excerpt of Deck 4 (indices as published):

```jsonc
"routing": {
  "walkingSpeedMps": 1.1,
  "decks": [
    {
      "deckNumber": 4,
      "nodes": [
        [88, 19.5, "elevator_lobby", "elev-fwd-4"],        // 0
        …
        [78, 14.04, "entrance", "v4-theatre", 0],          // 3: feature.entrances[0]
        …
        [96, 16.81, "entrance", "v4-photo", "projected"],  // 5
        …
        [83.7, 12.92],                                     // 26: corridor
        …
        [94.98, 17.15],                                    // 28: corridor
        …
      ],
      "walk": [
        [0, 28, 7.36],
        [3, 26, 5.81],
        [5, 28, 1.08],
        …
      ]
    }
  ],
  "elevators": [{ "bank": "fwd", "stops": ["elev-fwd-2", "elev-fwd-3", "…"] }],
  "stairs": [["elev-fwd-2", "elev-fwd-3", "…"], ["stairs-aft-7", "…", "stairs-aft-12"]]
}
```

| Field | Notes |
| --- | --- |
| `walkingSpeedMps` | Default pace for turning `lengthM` into time. A consumer may use its own. |
| `decks[]` | One entry per pack deck, same order, matched by `deckNumber`. |
| `decks[].nodes[]` | Node tuples, below. Coordinates are metres in pack coordinates, 2 dp. |
| `decks[].walk[]` | `[i, j, lengthM]` or `[i, j, lengthM, through]`. `i < j` index this deck's `nodes`. `lengthM` is the straight-line distance, 2 dp. |
| `elevators[]` | `{ bank, stops }`. `stops` are elevator feature ids, ascending by deck; each names the one `elevator_lobby` node for that feature. A bank joins **every pair** of its stops. |
| `stairs[]` | Feature-id lists, ascending by deck. Stairs join **neighbouring** stops only (one flight). |

### Node kinds

| Tuple | Kind | Meaning |
| --- | --- | --- |
| `[x, y]` | `corridor` | A point on a walkway centreline: a junction, bend, or spacing point. |
| `[x, y, "elevator_lobby", featureId]` | lobby | The landing of an elevator core. `featureId` is the `elevator` feature. The core's stairs land here too. |
| `[x, y, "stair", featureId]` | stair | The landing of a stairwell with no lifts (the aft stairwell on Decks 7–12). |
| `[x, y, "entrance", featureId, n]` | door | `feature.entrances[n]`, exactly. |
| `[x, y, "entrance", featureId, "projected"]` | projected door | A door the pack doesn't author, for a venue with no `entrances` (or none on the graph). See below. |

Nodes are ordered lobbies, stairs, doors, corridor, and by position within each group, so the
order is deterministic.

### Edge kinds

A consumer expands the block into three edge kinds. `expandRouting(pack)` in the generator does
exactly this; a port should match it.

| Kind | From | Cost inputs |
| --- | --- | --- |
| `walk` | `decks[].walk` | `lengthM`. Walk edges never change deck and are step-free. |
| `elevator` | every pair of stops in `elevators[].stops` | `decks`: levels between the two stops. Step-free. |
| `stairs` | neighbouring stops in `stairs[]` | `decks` (always 1 today). **Not** step-free. |

**All edges are undirected.** Nothing in v1 is one-way.

`decks` counts levels in `pack.decks` order, not deck numbers. The ship has no Deck 13, so
Deck 12 → 14 is one level. A step-free route uses `walk` and `elevator` edges only.

**`through`.** A walk edge that crosses a feature names it (see [Connectors](#connectors)). Every
other walk edge stays out of every venue, cabin and crew interior.

**Node identity.** Node indices are only stable within one `revision`. Stable references are
feature ids: a lobby by its elevator/stairwell id, a door by `featureId` plus `n` or `"projected"`.
Fixtures (P2.5) should route between those, not between corridor indices.

## Routing on it

[`src/utils/shipRouter.js`](../../src/utils/shipRouter.js) is the reference router: dependency-free
Dijkstra over the expanded graph. The maps site draws its routes with it, the fixtures below are
recorded with it, and AuraTrip's TypeScript port must match it.

**Endpoints.**

| Endpoint | Resolves to |
| --- | --- |
| `{ featureId }` | Every door of that venue on the graph (the cheapest wins), or an elevator or stairwell's landing. |
| `{ deck, at: [x, y] }` | The nearest `corridor` node on that deck (the cabin snap rule). The snap distance **is** added to the walk, at both ends. |
| `{ deck, elevators: true }` | Every connected elevator lobby on that deck (the cheapest wins). |

**Cost is time, in seconds.**

| Edge | Cost |
| --- | --- |
| `walk` | `lengthM / walkingSpeedMps` |
| `elevator` | `elevatorBoardS` (60) + `elevatorPerLevelS` (8) × `decks` |
| `stairs` | `stairsPerLevelS` (30) × `decks` |

The lift numbers are guesses (see the roadmap's risks). They make stairs win for one or two decks
and lifts win from three. Ties go to the lower node index, so a route is deterministic.

**Options.**

| Option | Leaves out | For |
| --- | --- | --- |
| `stepFree: true` | `stairs` edges | Step-free directions. |
| `avoidLifts: true` | `elevator` edges | A muster route: stairs only, never a lift. |

With both, only `walk` edges are left, so a trip to another deck or another walk section has no
route. The router returns `null` then. It never falls back to stairs or lifts: a caller that ruled
both out must be told there is no route.

**The Magic Carpet counts as a lift.** It is a moving platform, and no way out in an emergency, so
a stairs-only route must never ride it. Today the graph has no ride between its stops: each stop is
a venue on its own deck, reached on foot, so no route rides it, with or without `avoidLifts`. If a
pack ever adds the ride, it must be an `elevators[]` bank, which `avoidLifts` leaves out. The tests
hold the graph to that.

**Result.** `walkM` (walk edges plus snaps), `timeS`, and `legs` in order: `walk` legs (`deck`,
`points`, `lengthM`, `through`) and `elevator`/`stairs` legs (`fromDeck`, `toDeck`, `from`/`to`
feature ids, `levels`, and `bank` for lifts). Consecutive stairs flights merge into one leg.
`deckChanges` is `[{ mode, fromDeck, toDeck }]`, one entry per non-walk leg. A same-deck trip
between walk sections has two.

## Route fixtures

`v1/ships/<id>/route-fixtures.json` is published beside the pack. It is the routing contract
between this repo and ports.

```jsonc
{
  "specVersion": 1,
  "shipId": "celebrity-xcel",
  "recordedAgainstRevision": "c2b64fbc5010",   // informational
  "costModel": { "walkingSpeedMps": 1.1, "elevatorBoardS": 60, "elevatorPerLevelS": 8, "stairsPerLevelS": 30 },
  "tolerance": { "walkM": { "abs": 2, "rel": 0.03 }, "timeS": { "abs": 5, "rel": 0.05 } },
  "routes": [
    {
      "id": "lifts-5-to-spice-cafe",
      "description": "…",
      "from": { "deck": 5, "elevators": true },   // or { "featureId" } or { "cabinId" }
      "to": { "featureId": "v5-spice-cafe" },
      "stepFree": false,
      "expected": { "walkM": 46.44, "timeS": 42.2, "deckChanges": [], "through": ["v5-bazaar-market"] }
    }
  ],
  "avoidLiftsRoutes": [
    {
      "id": "le-voyage-to-theatre-4-step-free-no-lifts",
      "description": "…",
      "from": { "featureId": "v4-le-voyage" },
      "to": { "featureId": "v4-theatre" },
      "stepFree": true,
      "avoidLifts": true,
      "expected": null                              // no route, and no fallback
    }
  ]
}
```

- A `cabinId` end means "that cabin's pack `center`, snapped".
- A port passes a case when `deckChanges` and `through` (sorted, de-duplicated) match exactly,
  and `walkM` and `timeS` are each within `max(abs, rel × expected)`.
- The 26 Xcel cases cover walking only, stairs vs lifts (with step-free twins), consecutive
  flights, Deck 12 → 14, lift-only walk sections on one deck, every connector kind, the long
  Edge Villa snap, and cabin to cabin.
- Since P7.3, 12 of them go to the port exits (`portExit`): from cabins on Decks 3, 8 and 15 to
  the gangway and the tender platform, each with a step-free twin (`cabin-3-to-gangway-2` …
  `edge-villa-15-to-tender-platform-2-step-free`).

**`avoidLiftsRoutes`** holds the `avoidLifts` cases (P7.4). An entry has the same shape as a
`routes[]` entry, plus `"avoidLifts": true`: route it with `{ stepFree, avoidLifts }`.

- They are kept out of `routes[]` on purpose. A port runs every `routes[]` entry with `stepFree`
  alone, so it would fail them until it has the option. Each new router option gets its own
  top-level array the same way.
- `expected: null` means the port must find no route, not fall back. Only a case that is also
  step-free may have it.
- The 5 Xcel cases cover stairs where a lift would be quicker, Deck 12 → 14 by stairs, two walk
  sections of one deck joined by stairs, and step-free without lifts: a walk within one walk
  section, and no route beyond it.

**The file is recorded, not re-exported.** `scripts/route-fixtures.test.mjs` runs the router
against the committed pack and fails when a result leaves tolerance. So a layout, graph or router
change shows up as a failing test instead of a quiet diff. When the change is intended (e.g.
P1.1 moves venues), re-record and say why in the PR:

```sh
npm run record:route-fixtures
```

The cases live in `ROUTE_FIXTURE_CASES` and `AVOID_LIFTS_FIXTURE_CASES` in
[`scripts/route-fixtures.mjs`](../../scripts/route-fixtures.mjs).

## How it is built

1. **Walkable space.** Walkways aren't features on public decks: they are the gaps between
   rectangles, plus elevator lobbies, stairwells and the atrium (tag `Atrium`). Each deck is
   rasterised at 0.25 m. A point is walkable when it is inside the hull and at least **0.55 m**
   from the hull and from every feature that isn't circulation. So a passage must be at least
   1.1 m wide. Drawing seams are 1 m or less, so they're not walkways. The bow's staggered cabins
   pinch stateroom corridors to about 1.35 m, which still counts as walkable.
2. **Centrelines.** The walkable raster is thinned to its centreline and traced into straight
   edges. Runs of corridor nodes are string-pulled: a run is replaced by the fewest straight legs
   that stay on walkway, cutting no corner by more than 4 m.
3. **Lobbies and stair landings** join the nearest centreline point.
4. **Connectors** are added (below).
5. **Walk sections without a lobby are dropped.**
6. **Doors.** Each `feature.entrances` point joins the centreline along a line that keeps 0.3 m
   off every wall once it leaves the door. A door that opens onto a dropped section is left out
   (61 of the pack's 85 are on the graph). The venue still has a door elsewhere; the tests check
   that.
7. **Projected doors.** Every `venue`, `poi` or `muster_station` feature with no door on the graph
   gets one. The generator samples the venue's boundary, keeping points 0.55 m clear of every
   other feature, and picks the point with the shortest clear line (≤ 16 m) onto the graph, the
   middle of a face breaking ties. The node sits on the venue's wall, flagged `"projected"`.
8. **Pruning.** Dead ends that end at no door, lobby or stair are pruned. A dead end that is the
   last walk edge within 12 m of some cabin is kept, and trimmed back to what that cabin needs.
9. **Spacing.** Walk edges within 12 m of a cabin are split so no edge is longer than **16 m**.

Everything is deterministic, so an unchanged layout re-exports to the same bytes and `revision`.

### Walk sections

The synthetic layout doesn't join every part of every deck. Full-beam venues and crew blocks cut
some decks into sections between elevator cores:

- Deck 2: Medical Center, crew areas and stores
- Deck 4: Le Voyage and the Casino
- Deck 5: shops and the Galley
- Deck 14: the Solarium and Oceanview Café
- Deck 15: the Retreat Lounge, Fitness Center, Bora and Rooftop Garden
- Deck 16: the Retreat Lower Sundeck

The graph keeps those sections as they are drawn. **Every walk section contains an elevator
lobby.** A same-deck trip between two sections goes via a lift, or via stairs if the consumer
allows them. That will change when the layout does (P1.1).

Every lobby is also a stair landing, so stairs join the same sections the lifts do. A stairs-only
route reaches every section, on every published ship.

### Connectors

A few doors open onto sections that have no lobby at all. `ROUTING_CONNECTORS` links each one,
with its reason. Each is a documented modelling decision, not geometry:

| Deck | Links | How |
| --- | --- | --- |
| 4 | Mosaic at The Bazaar | Along the 0.4 m seam between Cosmopolitan and Cyprus, standing in for the walkway between two dining rooms. Crosses nothing. |
| 5 | Spice Café | `through` Market at The Bazaar: both are in the same open Bazaar hall. |
| 14 | Aft Sun Deck | Along the 0.4 m seam at the edge of the Oceanview Café Terrace. Crosses nothing. |
| 17 | The Retreat Bar | `through` the Retreat Sundeck it serves. |
| 2, 5, 14, 16 | Magic Carpet stops | `through` the venue each stop extends (Destination Gateway, World Class Bar, Pool Club Cabanas, Glass-Walled Hot Tubs), ending at a projected door on the hull edge. |

The tests hold this list to exactly what's needed. Removing any one connector must leave a venue
unreachable, and `through` is only allowed on connector edges.

**Restricted areas.** A route never crosses a feature whose `access` is `suite`, `adults` or `kids`
unless its destination has the same `access`. Today that crossing is only the Retreat Bar, reached
across the Retreat Sundeck, and both are suite-only. `paid` doesn't keep anyone out, so a route may
pass one: the Deck 14 Magic Carpet stop is reached along the cabana row. The fleet-wide test in
`scripts/routing-graph.test.mjs` checks every venue on every published ship.

**Port exits.** On every published ship, every cabin reaches every `portExit` feature, with and
without stairs. The same test file routes every one of those pairs. On Xcel both exits are in
Deck 2's midship walk section, so every route arrives by the midship lifts or stairs. The
tender exit on Edge-series ships is the Deck 2 Magic Carpet stop, reached through Destination
Gateway on the connector above. The graph counts that link as a walk. A 2018 account of Celebrity
Edge describes a short stairway there with a stairlift, so a wheelchair route depends on that lift.

## Elevator bank service

Derived from which elevator features each deck draws (a core the deck's hull can't hold isn't
drawn). Not every bank serves every deck.

| Bank | Decks |
| --- | --- |
| `fwd` | 2–12, 14–17 |
| `mid` | 2–12, 14–16 |
| `aft` | 2–12, 14–15 |
| Aft stairwell (`stairs-aft`, stairs only) | 7–12 |

Every elevator core also has stairs between neighbouring served decks. Elevator and stairwell
positions are `positionConfidence: "estimated"`.

## Cabins: the snap rule

There are **no cabin nodes**. To route to or from a cabin, snap its `center` to the **nearest
`corridor` node on its deck**, by straight-line distance.

- Walk edges within 12 m of a cabin carry a corridor node at least every **16 m**.
- Every cabin centre is within **15 m** of a corridor node. The exceptions are the four Deck 15
  Edge Villas (15100–15106), whose only walkway is the forward lobby; they are within 40 m.

The snap distance isn't walked. It is the cabin's own corridor, so treat it as zero or add it, as
the consumer prefers.

## What the tests guarantee

`scripts/routing-graph.test.mjs`, against the pack as built and as committed:

- `specVersion` is 1. Everything outside `routing`, `revision` and `updatedAt` hashes identically
  to `main` before routing, so aliases, spans, confidence and entrances are unchanged.
- The committed `plan.json` matches a fresh export, so the export is byte-stable.
- Tuples are well formed and rounded to 2 dp.
- No dangling edges, duplicate edges, self-loops or cross-deck walk edges.
- Only the Deck 2 aft lobby is isolated: it opens onto crew space only.
- Every walk edge's `lengthM` is its straight-line length ±0.05 m.
- Every node is inside its deck's hull.
- Sampled every 10 cm, no walk edge leaves the hull or enters any venue, cabin or crew interior,
  except a connector crossing the one feature it names.
- Every entrance node is a real `feature.entrances` point or flagged `"projected"`, on the wall of
  an existing guest feature. Every guest venue has at least one door on the graph.
- Every elevator and stairwell feature has exactly one node, inside its footprint. Bank service is
  exactly the table above, and stairs are never step-free.
- Every walk section on every deck contains an elevator lobby.
- From every elevator lobby, every door on the ship is reachable **without stairs**.
- On every published ship, every cabin reaches every port exit, with and without stairs.
- From every cabin, where it snaps, every guest venue on the ship is reachable **without lifts**.
  This holds on all 14 published ships. A gap here is a missing stair link to fix, never a reason
  to fall back to a lift.
- Only an `elevator` edge may join the Magic Carpet's stops across decks.
- Every connector is necessary.
- The cabin snap distances and node spacing above hold.
- Size budget, below.

## Size

The budget is **≤ 15 % gzipped growth** of `plan.json` over a recorded baseline,
`scripts/pack-size-baseline.json`: `main` before routing, 59,100 bytes gzipped (Node `zlib`
default level). The exporter's summary line prints raw and gzipped size before → after on every
run.

| `plan.json` | Raw | Gzipped |
| --- | --- | --- |
| Before routing | 619,443 B | 59,100 B |
| With routing | 640,790 B (+3.4 %) | 63,547 B (+7.5 %) |

The first draft used plain objects (`{ "id", "deck", "at", "kind" }` nodes and `{ "from", "to",
"kind", "lengthM" }` edges, with pairwise elevator edges). It came to about 13 KB gzipped, +22 %.
That is why nodes are tuples, deck is implied by grouping, edges use indices, and elevators and
stairs are stop lists.

**Updating the baseline.** Only do it deliberately, in a change that justifies the growth (e.g. a
new feature field the budget should absorb). Re-record `gzipBytes` and `rawBytes` from `main`
*before* your change, run `npm test`, and say why in the PR. Never raise it just to make routing
fit.
